What works today, and what's next

Here is what agent-heavy teams say gets in the way, and where Taru stands on each.

Works today

  • A Git server of your own. Create a repo, then git push and git clone over HTTPS. Every CI run has the stock git client push a real-shaped repo, clone it back and check that the commits and files match.
  • No clone for every agent. Agents read files, commit and merge through a REST API, or call the same operations as MCP tools, with no checkout, worktree or disk.
  • Merges on the server. A three-way merge, tested against git merge-tree. A conflict writes nothing and goes back to the agent as a report, file by file.
  • You don't leave GitHub. Import a GitHub repo, and Taru copies every change back to it, one way, about a second later.
  • GitHub outages, partly. Push, clone and the API run in your Cloudflare account and don't touch GitHub. Cloudflare has outages too.
  • Large files. Files over 512 KB go to R2, which has no egress fees.

Who can see your code today: anyone who can reach your server can list, read and clone every repo, and one admin token controls pushes, API commits and new repos. Use Taru for public code and experiments for now. Accounts with GitHub sign-in come in a later step.

Next

  • Private code in a public repo. The server will decide who sees which folders, and the GitHub copy will leave private ones out.
  • .env files and shared secrets. Secrets will be encrypted, kept out of history, and handed only to the people, agents and CI that need them.

Later

  • Review that can't keep up. A review app for agent changes. Until then, review stays on GitHub.
  • Agent workspaces. A CLI with automatic snapshots and instant local workspaces.

Git and GitHub keep working

  • Use the git you already have. Clone, fetch, pull and push work over HTTPS with the same commit ids, and there's nothing to install.
  • Every push is copied, one way, to a GitHub repo you own. Actions, issues and stars stay on GitHub.
  • Leave whenever you like. It's plain Git, so git clone --mirror takes the whole history with you.

Not yet: SSH, shallow or partial clones, pushes over 100 MB, and importing or copying a repo with more than 48 MiB of Git objects. So CI that clones straight from Taru needs a full clone.

Questions

What happens to my repos if Taru stops?
They're plain Git, so git clone --mirror and git push --mirror move them to any host. The server runs in your Cloudflare account, so it keeps running if the project stops, and the AGPL lets anyone carry it on.
Does the AGPL apply to my code?
No. It covers Taru's own code, not the repos you keep in it. If you change Taru and let people use your version over a network, you offer them its source. Running it unchanged for your team asks nothing of you. That's a plain reading, not legal advice.
Does Taru see my code or train on it?
No. There's no Taru service in the middle. The server runs in your account, has no telemetry and sends nothing to us. Refs and commits live in a Durable Object per repo, and large files in your R2 bucket.
How is it different from Cursor Origin or Cloudflare Artifacts?
Cursor hosts Origin for you, and Cloudflare runs Artifacts as storage it bills per operation. Taru is open source and runs in your own account. Around the storage it gives people plain git, agents an API and MCP tools, and you a copy on GitHub.
Where do the ideas come from?
From Anthropic's post on Scion, the system that replaced git for their monorepo: the server does the heavy work, files are stored by content, and every query the client makes is also an API call. Taru takes the ideas, not the scale, and laptops keep plain git.
