One commit, three places

This is the flow Taru is built around. An agent will change code without a checkout, and the result will be a normal Git commit that your laptop and GitHub both see.

  1. Building now

    An agent sends its change

    One API request will carry the files the agent changed and a commit message. With no clone, worktree or disk, ten agents won't need ten checkouts.

  2. Building now

    Taru writes a real commit

    The server will write the blobs, trees and commit, then move the branch, inside the repository's Durable Object. Pushes are stored this way today: each file once, by hash, and files over 512 KB in R2.

  3. Works today

    Everyone else sees plain Git

    A laptop runs git pull and gets the same commit id. The copy to your GitHub repo, one way from Taru to GitHub, is being built.

The ideas come from Anthropic's post on Scion, the system that replaced git for their monorepo: the server does the heavy work, files are stored by content, and every query the client makes is also an API call. Taru takes the ideas, not the scale, and laptops keep plain git.

Git and GitHub keep working

  • Use the git you already have. Clone, fetch, pull and push work over HTTPS with the same commit ids, and there's nothing to install.
  • Every push will be copied, one way, to a GitHub repo you own. Actions, issues and stars stay on GitHub.
  • Leave whenever you like. It's plain Git, so git clone --mirror takes the whole history with you.

Not yet: SSH, shallow or partial clones, and pushes over 100 MB. So CI that clones straight from Taru needs a full clone.

Where it is

Taru is early. git push and git clone work today. Every CI run has the stock git client push a real-shaped repo to Taru's Git engine, clone it back and check that the commits and files match.

  1. Core: create a repo, git push and git clone Works today
  2. Import from GitHub, and the automatic copy to GitHub Building now
  3. Agent API and MCP server: read, edit, commit and merge with no clone Building now
  4. Private folders and secrets
  5. Review web app
  6. CLI: automatic snapshots and instant agent workspaces

Who can see your code today: anyone who can reach your server can list every repo and clone it, and one admin token controls pushes and new repos. Use Taru for public code and experiments for now. Accounts with GitHub sign-in come in a later step.

Questions

What happens to my repos if Taru stops?
They're plain Git, so git clone --mirror and git push --mirror move them to any host. The server runs in your Cloudflare account, so it keeps running if the project stops, and the AGPL lets anyone carry it on.
Does the AGPL apply to my code?
No. It covers Taru's own code, not the repos you keep in it. If you change Taru and let people use your version over a network, you offer them its source. Running it unchanged for your team asks nothing of you. That's a plain reading, not legal advice.
Does Taru see my code or train on it?
No. There's no Taru service in the middle. The server runs in your account, has no telemetry and sends nothing to us. Refs and commits live in a Durable Object per repo, and large files in your R2 bucket.
How is it different from Cursor Origin or Cloudflare Artifacts?
Cursor hosts Origin for you, and Cloudflare runs Artifacts as storage it bills per operation. Taru is open source and runs in your own account. Around the storage it gives people plain git today, and an API for agents and a copy on GitHub are being built.
