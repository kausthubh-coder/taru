GitHub alternative researchOctober 12, 2026Explainer

Git keeps the history; GitHub sells everything around it, and that's where both the lock-in and the complaints are

Before building a GitHub alternative, you need to know what each part does, how GitHub makes money, who uses it, and which problems actually make people pay or leave.

  • Git is free software on your machine. It stores snapshots of your code and labels pointing at them. It has no accounts, reviews, issues or CI.
  • GitHub is a website (a "forge") that hosts Git repos and adds everything Git leaves out: who can push, pull requests, review, issues, CI (Actions), and a public profile. Most of what you'd call "GitHub" isn't Git.
  • Lock-in lives in the forge layer. git clone copies the code in seconds, but PRs, reviews, issues, CI setups, integrations and the contributor community don't come with it.
  • Money comes from companies: per-seat plans, Copilot, CI minutes. Individuals and open source are the free funnel. 90% of the Fortune 500 use GitHub.
  • The 2026 pain comes from AI agents. They write far more code, which overloads GitHub's servers (outages) and human reviewers (review queues, AI-generated junk PRs). The loudest complainers are open-source maintainers who don't pay. The teams that do pay stay on GitHub and buy tools on top.

Ten words the rest of the page depends on

Commit
A saved snapshot of every file in the project, plus a pointer to the commit before it, the author and a message. It's named by a hash such as a1f9c03, computed from its contents. Change anything, including its parent, and the hash changes.
Branch
A movable label pointing at one commit, nothing more. Making a branch writes a 41-byte file, which is why branches are cheap in Git.
Repository (repo)
The folder of commits and labels. Every clone holds the full history, so your laptop has as much as the server does.
Remote
Another copy of the repo you push to and pull from, usually on GitHub. Calling it "the server" is just a convention; to Git it's another copy.
Forge
A website that hosts repos and adds collaboration: GitHub, GitLab, Bitbucket, Codeberg, Forgejo.
Pull request (PR)
A forge feature, not a Git one: "please merge my branch into main." It's the page where people discuss, review and approve a change.
CI (continuous integration)
Machines that build and test every change automatically. GitHub's CI is called Actions and is configured in YAML files.
Merge queue
A line of approved PRs. The forge tests them together before merging, so two PRs that each pass alone can't break main together.
Stacked PRs
One big change split into a chain of small PRs, each building on the last, reviewed one at a time. GitHub shipped them on every plan on October 6, 2026.
Agent
An AI coding tool (Claude Code, Codex, Copilot, Cursor) that writes code and opens PRs itself. Microsoft said in July 2026 that 1 in 3 PRs on GitHub involves one.

Git is a chain of snapshots plus movable labels

Linus Torvalds wrote Git in 2005 for Linux kernel development. Every operation you use daily (commit, branch, log, diff, merge) runs on your machine with no network. Pushing and pulling just copy missing commits between two repos.

Here is a real-shaped example. You branch off at commit B to build a feature. Meanwhile someone adds commit C to main. Your branch has D and E.

Rebase replays D and E on top of C. Because a commit's hash covers its parent, the copies get new hashes. The label moves; the old commits are just left behind.

That one behavior explains a lot of the pain later on. Review tools attach comments to commit hashes, so every rebase or amend makes them look like brand-new commits. Gerrit (used by Google's Android team) adds a fixed "Change-Id" to each commit. Jujutsu (jj) gives every change a stable ID that survives rewrites. GitHub reviews a whole branch's diff instead, which is why long-running PRs get messy.

What Git deliberately doesn't do

Git only answers "what did the code look like, and how did it get here?" It has no idea who you are. These all come from the forge:

  • Accounts and permissions: who may push, who may approve.
  • Review: comments, approvals, "request changes".
  • Issues and planning: bug reports, roadmaps, projects.
  • CI: running tests on every push.
  • Discovery: search, stars, profiles, forks.

Jujutsu (jj) is a different front end on the same storage

jj stores data in Git format and pushes to normal Git remotes, including GitHub. What changes is how you work. Your working folder is always a commit, so nothing needs staging. Changes have stable IDs. A conflicting rebase still succeeds and records the conflict to fix later. Editing a commit automatically rebases everything after it. There's a full undo log. It has about 32,000 GitHub stars, and its creator joined the funded startup ERSC as CTO in September 2026. Because it works with GitHub, it fixes Git's usability without moving you off GitHub.

GitHub is down for three hours. Can you still commit, branch and read history?

Yes. Those are all local Git operations. What you lose is the forge: you can't open or merge PRs, get reviews, or run Actions. That's why outages hurt teams so much: Git is fine, but shipping goes through the forge.

A reviewer commented on commit d4e. You rebase and force-push. What happens to the comment?

d4e is no longer on the branch; it's been replaced by 7f1. The comment gets marked "outdated" or ends up pointing at nothing. That's the reason stable change IDs (jj, Gerrit) exist and why GitHub's stacks had to keep approvals working through rebases.

One change, end to end: the loop every team runs, with agents now at both ends

Here's what happens when a teammate, or an agent, fixes a bug at a typical company on GitHub. Highlighted steps are where the work has piled up since agents arrived.

  1. Branch: create fix-login from main. Outside contributors without write access fork the repo first.
  2. Commit: edit and save snapshots locally. An agent may run several of these in parallel, each in its own worktree (an extra checkout of the same repo). Theo calls worktrees "an abomination" for this.
  3. Push: send the commits to GitHub.
  4. Open a PR: describe the change and request reviewers. CODEOWNERS adds required reviewers automatically. Agents now open PRs on their own: the Copilot agent alone opened over 1M between May and September 2025.
  5. Checks run: Actions builds and tests. A failure means push a fix and wait again. This "push and wait" loop is the most complained-about part of GitHub.
  6. Review: a human reads the diff, comments, approves or asks for changes. Feedback to an agent is usually relayed by hand: a person copies the comment back into the agent's session. This is the new bottleneck.
  7. Merge queue: approved PRs are tested together against the latest main, then merged.
  8. Deploy: usually another Actions workflow ships it.

Steps 1-3 are Git. Steps 4-8 are GitHub. In one 2025 study of 10,000+ developers (Faros AI, via secondary summaries), teams that used AI heavily merged 98% more PRs, but PR review time rose 91% and average PR size rose 154%, with no measurable improvement in company-level delivery. Writing code got cheap; steps 4-6 didn't.

An agent opens 30 PRs overnight. Which step does a two-person team get stuck on?

Review (step 6), and to a lesser degree CI (step 5). Writing and pushing cost almost nothing now. Humans still have to decide which PR to look at first, read it, and relay feedback. That's why "faster code generation" isn't the opening for a new product, but the review queue is.

GitHub won on timing and taste, and people stay because of everything that isn't code

How it won

In 2005 most projects used SVN, where one central server held the history and contributing meant emailing patch files. Git and Mercurial both arrived that year and made branching cheap. GitHub launched in 2008 with two things competitors lacked. One was a user-centric design: projects live under people's names, and anyone can fork and send a pull request. The other was taste: it wasn't ugly. The Ruby on Rails community adopted it early. By December 2008 GitHub had about 27,000 public repos to Bitbucket's 1,000. Google Code shut down in 2015 and pointed people to GitHub. Bitbucket dropped Mercurial in 2020 because fewer than 1% of new users picked it.

Why people stay: what does and doesn't come with you

Comes with git clone
  • Every file and every commit
  • Branches and tags
  • Commit messages and authors

Moving this takes minutes.

Stays on GitHub
  • PRs and reviews: years of discussion about why code is the way it is
  • Issues and the links between them
  • Actions workflows and Marketplace actions
  • Integrations: Slack, Linear, Vercel, deploy hooks, GitHub Apps
  • Rules: branch protection, CODEOWNERS, SSO and permission setups
  • People: contributors' accounts, stars, followers, Sponsors money

The deepest moat is the bottom bullet. "There are plenty of places to host a Git repository, but remarkably few places to host an open-source community," as one widely shared post put it. Contributors already have GitHub accounts, dependencies live there, and every agent defaults to GitHub's APIs. Leaving means asking everyone to follow you.

A team mirrors its repo to Forgejo in an afternoon. Why might it still be on GitHub a year later?

The mirror moved the cheap part. CI pipelines need rewriting, PR history and issue links stay behind, integrations need reconnecting, and outside contributors have to make new accounts. Ghostty is the live example: it announced it was leaving in April 2026 and is still developed on GitHub every day in October.

Large OSS maintainers have the worst pain. Why aren't they the first customer?

They don't have budgets. Pain alone doesn't make a customer: you need pain, money and someone who can install the tool in five minutes, all in one person. At a small AI-heavy startup, the tech lead is all three. Maintainers are still valuable as free design partners and word of mouth, the way CodeRabbit gives its tool free to 150,000 open-source projects.

Each problem in more detail

Reliability Azure migration plus agent load; status page vs third-party numbers

GitHub started moving off its own Virginia data centers to Azure in October 2025, during the agent traffic surge. Its own post (April 2026) called two incidents "not acceptable" and set priorities as "availability first, then capacity, then new features."

  • Incident counts: isgithubcooked.com, a third-party tracker, shows about 23 incidents a month recently and 37 in February 2026. Trailing 3-month uptime: Actions 98.21% (about 6.5 days down), PRs 98.49%, Git operations 99.51%. GitHub's own status page shows about 99.9%. The two count differently, and neither is an independent measurement.
  • Correctness, not just downtime: on April 23, 2026 a feature leaking past a flag made squash merges in the merge queue revert earlier merges. That hit 2,092 PRs in 658 repos, and GitHub "could not safely repair every repository automatically." Silent wrong code on main is what companies fear most.
  • Security: CVE-2026-3854 allowed remote code execution through git push; about 3,800 internal GitHub repos were breached in May 2026 through an employee's malicious VS Code extension.
Actions CI YAML, the push-and-wait loop, the pricing scare, supply-chain attacks
  • Debug loop: you can't run the pipeline locally the same way, so you push, wait, read logs, and push again. The log viewer has been reported to crash browsers.
  • Config: YAML plus GitHub's own expression language; confusing caching where misses are silent; a hard-to-follow token permissions model.
  • Pricing scare: in December 2025 GitHub announced $0.002 a minute for self-hosted runners, about $86 a month for a runner that's always on. It backed off within about 48 hours, but trust took the hit.
  • Supply chain: in March 2025 the popular tj-actions/changed-files action was hijacked to dump secrets into logs. About 23,000 repos used it.
  • Counterpoint: it's still "one of the best free CI services in the world." Free CI is a reason people stay.
Review overload and AI junk PRs the problem with money behind it
  • Open source: curl ended its bug bounty in January 2026 after a flood of AI-written reports. Godot's co-founder and the RPCS3 team asked people to stop sending AI PRs. tldraw auto-closes outside PRs. One maintainer estimated only about 1 in 10 AI-created PRs is legitimate.
  • GitHub's response: a setting to disable PRs or limit them to collaborators, plus discussion of AI triage and disclosure labels.
  • Companies: the problem isn't junk, it's volume. A team's own agents produce more PRs, bigger PRs and branches that conflict with each other. People still pick what to review next and relay feedback by hand.
  • Money: Cursor bought Graphite (stacked PRs and review) in December 2025; CodeRabbit raised at a reported $1.5B valuation in August 2026; former GitHub CEO Thomas Dohmke's Entire raised a $60M seed on "PRs don't scale for agent code."
AI push and trust why some people are angry at GitHub for opposite reasons

Two groups are angry about AI for opposite reasons. Anti-AI maintainers (Zig, Codeberg members, Gentoo) object to Copilot being pushed at them. In March 2026 Copilot inserted promotional "tips" into 11,400+ PRs, including ones humans wrote, and GitHub switched it off the same day. From April 2026, Copilot interaction data on Free/Pro plans is used for training unless you opt out. AI-heavy users object to the outages and to being banned elsewhere: Codeberg's members voted 358 to 144 in July 2026 to ban mostly-AI-written projects. The anti-AI group switches but pays with effort, not money. The AI-heavy group has budgets.

Theo's four asks the clearest statement of "Git is the wrong tool for agents"

In May 2026 Theo posted "GitHub is dying and git is not the right primitive" and asked someone else to build the fix. His points map to four product ideas:

  1. Partial privacy: private folders and unreleased security fixes inside a public repo.
  2. No bookkeeping: "Commits are a bad primitive. Branches are worse." He wants jj-style automatic snapshots.
  3. Cheap parallel checkouts: "Worktrees are an abomination." Agents need copy-on-write workspaces.
  4. API access: reading and writing source without a full OS and filesystem.

Caveats: he isn't building it, he's sponsored by CI vendors, and he recommended Codeberg and then turned on it within two months. Treat his posts as a signal from agent-heavy TypeScript developers, not as neutral evidence.

Why are stacked PRs a weak reason to build a GitHub alternative after October 6?

GitHub now ships them free on every plan, with approvals kept through rebases and merge-queue support. A team won't switch for something it already has. What GitHub still doesn't do is coordinate many agents: deciding which PR matters, sending review feedback back to the agent, keeping parallel branches mergeable.

The common mistake: "GitHub is a Git host, so a better Git host wins"

This is wrong, and it's the trap most GitHub alternatives fall into. Hosting Git is the easy, portable, cheap part. GitHub's grip comes from the community graph, free CI, years of PR and issue history, integrations and permission setups. A faster, nicer host still asks every user to give all of that up at once.

The evidence agrees. The projects that left are ones willing to lose contributors. Companies with money don't leave; they buy tools that sit on GitHub. And the newest funded entrants either sync both ways with GitHub (Cursor Origin) or mirror it (Entire) instead of asking for a hard switch. A new product wins by fixing one painful job for people who pay, working with GitHub on day one, and becoming a full forge only once users already depend on it.

What this means for you: the open gap is coordinating agents' work, not hosting it

Put together, the page points one way:

  • Who: the tech lead at a 2-20 engineer startup whose agents out-produce its reviewers. Large OSS maintainers as free design partners.
  • What: triage that decides which agent PR to look at first, review feedback sent straight back to the agent through a CLI or MCP, and keeping parallel agent branches mergeable. Work with GitHub, don't replace it.
  • Not: stacks (GitHub has them), generic AI review comments (CodeRabbit and Copilot), or a new forge first (high switching cost, low price ceiling).
  • Later: Theo's asks (privacy, snapshots, copy-on-write workspaces) and a self-hostable forge, once teams rely on you.

A founder says "we'll beat GitHub with faster pages and no outages." What's the first question to ask?

"Who pays, and what do they give up to switch?" Faster pages help, but the paying team would lose CI, PR history, integrations and its contributors to get them. Unless the product works alongside GitHub, or fixes something painful enough to justify that cost, speed alone won't move them. GitHub is also already fixing page speed.
